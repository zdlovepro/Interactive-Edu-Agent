# 1. 引言

## 1.1 编写目的

本文档旨在明确“基于泛雅平台的 AI 互动智课生成与实时问答系统”的功能需求、非功能需求、接口要求、运行环境、数据对象及验收标准，为项目的设计、开发、测试、规模度量以及后续与超星泛雅网络教学平台的集成提供基准。

本文档既作为开发团队的需求依据，也作为后续软件规模度量、功能点分析、测试验收和项目交付的参考文档。

---

## 1.2 项目背景

在教育数字化转型的背景下，个性化学习与高效知识传递成为在线教育平台的重要发展方向。当前泛雅平台积累了大量 PPT、PDF 等优质教学资源，但传统静态课件存在讲授模式固化、互动性弱、学习节奏难以个性化调整等问题。

本项目旨在依托泛雅平台，引入大模型、语音识别、语音合成、RAG 检索、实时问答和智能断点续播等技术，通过“课件解析 - 内容重构 - 智能讲授 - 实时问答 - 进度续接 - 学习诊断”的流程，将静态课件转化为具备交互能力的智能课程。

---

## 1.3 目标用户

### 1.3.1 教师

教师是内容创建者和课程管理者，主要需求包括：

1. 快速上传已有 PDF、PPT、PPTX 课件；
2. 自动解析课件内容；
3. 自动生成结构化讲稿；
4. 查看、编辑和校验 AI 生成的讲稿；
5. 启动 AI 智课讲授；
6. 查看学生提问记录、答疑记录和学习进度。

### 1.3.2 学生

学生是课程学习者，主要需求包括：

1. 进入 AI 互动课堂；
2. 听取课件内容讲解；
3. 在学习过程中通过文字或语音随时提问；
4. 获得与当前课件内容相关的智能回答；
5. 查看回答依据和相关课件来源；
6. 在答疑结束后继续原来的学习进度；
7. 查看自身学习进度和知识点掌握情况。

# 2. 总体描述

## 2.1 产品定位

本系统是面向泛雅平台和学习通场景的 AI 互动智课系统，定位为：

> 将静态课件自动转化为可讲解、可提问、可中断、可续播、可诊断的智能课程。

系统核心价值包括：

1. 降低教师制作互动课程的成本；
2. 提升静态课件的讲授效果；
3. 支持学生在学习过程中实时提问；
4. 基于课件上下文生成准确回答；
5. 根据学习状态动态调整教学节奏；
6. 为泛雅平台提供轻量化集成能力。

---

## 2.2 运行环境

### 2.2.1 客户端支持

系统应支持以下客户端环境：

1. 泛雅平台 Web 端；
2. 学习通移动端 H5；
3. 独立 Web 演示端。

### 2.2.2 浏览器要求

由于系统需要使用 WebSocket、SSE、MediaRecorder、Web Audio API、麦克风权限和 HLS 播放能力，因此不再支持 IE 浏览器。

推荐浏览器：

1. Chrome 100+；
2. Edge 100+；
3. Safari 15+；
4. Android Chrome 100+；
5. iOS Safari 15+。

### 2.2.3 特殊浏览器能力要求

1. 语音打断功能需要浏览器支持 `getUserMedia`；
2. 录音功能需要浏览器支持 `MediaRecorder`；
3. VAD 语音活动检测需要浏览器支持 Web Audio API；
4. SSE 流式问答需要浏览器支持 EventSource 或兼容方案；
5. 麦克风采集功能需要 HTTPS 环境或 localhost 环境；
6. HLS 视频播放在部分浏览器中需要 HLS.js 或 Video.js 支持。

---

## 2.3 服务端及资源要求

### 2.3.1 基础硬件配置

建议服务端配置：

1. CPU：8 核及以上；
2. 内存：16GB 及以上；
3. 存储：500GB 及以上；
4. 网络：下行带宽 ≥ 5 Mbps，上行带宽 ≥ 2 Mbps；
5. 网络延迟：≤ 100ms；
6. 丢包率：≤ 1%。

### 2.3.2 服务端组成

系统服务端由以下部分组成：

1. Java 后端服务；
2. Python AI 服务；
3. 前端 Web 服务；
4. 对象存储或本地文件存储；
5. 向量数据库或关键词 fallback 检索；
6. 可选的 Redis / 数据库 / 消息队列组件。

### 2.3.3 并发能力

系统应至少支持：

1. 10 人并发访问；
2. 多个课件并行上传与解析；
3. 多个课堂会话并行问答；
4. 课堂播放、语音打断和问答流程同时运行。

# 3. 核心功能需求

系统主要由以下模块构成：

1. 智课生成模块；
2. 实时问答交互模块；
3. 进度续接与节奏调整模块；
4. 平台集成与交付模块。

---

## 3.1 智课生成模块

### F1.1 课件上传

系统应支持教师上传课件文件。

功能要求：

1. 支持 PDF、PPT、PPTX 格式；
2. 保存课件名称、文件类型、文件大小、上传时间、上传状态；
3. 支持上传失败提示；
4. 支持上传成功后进入解析流程；
5. 支持查看已上传课件列表。

---

### F1.2 课件解析

系统应支持对上传课件进行智能解析。

功能要求：

1. 提取课件页码；
2. 提取页面文本；
3. 提取标题和段落结构；
4. 提取核心知识点；
5. 尽可能识别图表、公式、流程图和表格；
6. 保存每页解析结果；
7. 支持解析状态查询；
8. 解析失败时返回明确错误信息。

---

### F1.3 课件视觉内容提取

系统应支持对课件页面中的视觉信息进行补充识别。

功能要求：

1. 将 PPT/PDF 页面渲染为图片；
2. 识别图表、公式、流程图、表格等视觉对象；
3. 生成页面视觉摘要；
4. 将视觉摘要与对应页码绑定；
5. 在后续问答中支持引用视觉摘要；
6. 当视觉模型不可用时，应支持 mock 或降级策略。

---

### F1.4 脚本重构与生成

系统应基于课件解析结果生成结构化讲稿。

讲稿应至少包含：

1. 开场白；
2. 当前页核心讲解；
3. 页间过渡语；
4. 结束语；
5. 知识点标签；
6. 页面索引；
7. 讲解顺序。

功能要求：

1. 支持调用大模型生成讲稿；
2. 讲稿内容应与课件内容相关；
3. 讲稿应适合语音播报；
4. 生成失败时应提供 fallback 讲稿；
5. 讲稿生成结果应保存。

---

### F1.5 教师干预与编辑

系统应提供教师编辑和校验讲稿的能力。

功能要求：

1. 教师可以查看 AI 生成的结构化讲稿；
2. 教师可以修改每页讲稿；
3. 教师可以查看每页知识点；
4. 教师可以保存修改结果；
5. 教师可以重新生成讲稿；
6. 教师可以确认讲稿用于后续语音合成。

---

### F1.6 TTS 语音合成

系统应支持对讲稿进行语音合成。

功能要求：

1. 支持逐页讲稿批量 TTS 合成；
2. 将音频 URL 与对应讲稿页面绑定；
3. 支持查看音频生成状态；
4. TTS 失败时不影响讲稿查看；
5. TTS 不可用时前端可降级为 Web Speech；
6. 不得在日志中泄漏第三方服务 API Key。

---

### F1.7 数字人对接

系统应预留数字人对接能力。

功能要求：

1. 支持将讲稿文本和音频提交给数字人服务；
2. 支持生成音频时间轴；
3. 支持生成动作驱动协议；
4. 支持创建数字人视频任务；
5. 支持查询数字人视频任务状态；
6. 数字人服务不可用时应支持 mock 视频或降级播放。

---

## 3.2 实时问答交互模块

### F2.1 文字提问

学生应能够在课堂过程中通过文字输入问题。

功能要求：

1. 学生可以输入文本问题；
2. 系统接收问题后进入答疑状态；
3. 系统应结合当前课件内容生成回答；
4. 问答结果应保存；
5. 问答失败时应提供友好提示。

---

### F2.2 语音提问与 ASR

学生应能够通过语音打断课堂并提出问题。

功能要求：

1. 前端应支持麦克风权限申请；
2. 系统应支持录制学生语音；
3. 系统应通过 ASR 服务将语音识别为文本；
4. 当前设计采用 Qwen3-ASR-Flash 或本地 mock ASR 作为兜底；
5. ASR 失败时允许学生手动输入问题；
6. 系统不应长期保存原始录音，除非获得明确授权。

---

### F2.3 VAD 语音活动检测

系统应支持语音活动检测。

功能要求：

1. 检测学生开始说话；
2. 说话开始时暂停课堂讲解；
3. 静音达到指定时长后停止录音；
4. 支持配置静音阈值和静音持续时间；
5. 浏览器不支持时应提示用户手动输入问题。

---

### F2.4 WebSocket 课堂信令

系统应通过 WebSocket 支持课堂状态同步和打断信令。

功能要求：

1. 支持 heartbeat；
2. 支持 interrupt；
3. 支持 resume；
4. 支持 state_sync；
5. 打断时保存当前页码和播放时间；
6. 恢复时返回断点信息；
7. WebSocket 异常时不影响手动问答。

---

### F2.5 基于课件上下文的 RAG 答疑

系统应基于课件上下文进行问答。

功能要求：

1. 根据课件 ID 检索相关内容；
2. 根据当前页优先检索当前页和相邻页；
3. 使用 evidence 生成回答；
4. 如果课件中没有直接依据，应明确说明；
5. 回答应简洁、适合学生理解；
6. 不得编造课件中没有的信息。

---

### F2.6 evidence 来源展示

系统回答问题时，应返回证据来源。

功能要求：

1. evidence 应包含页码；
2. evidence 应包含引用片段；
3. evidence 应包含 chunk 或来源标识；
4. 前端应能展示 evidence；
5. 学生可查看回答依据。

---

### F2.7 SSE 流式回答

系统应支持使用 SSE 返回流式回答。

功能要求：

1. 支持 AI 回答按片段输出；
2. 前端实现打字机效果；
3. 支持流式结束标记；
4. 支持流式错误事件；
5. SSE 失败时可以降级为普通 POST 问答。

---

### F2.8 多轮追问

系统应支持围绕同一知识点的连续追问。

功能要求：

1. 保存最近若干轮问答上下文；
2. 追问时能够理解前文问题；
3. 多轮上下文不应无限增长；
4. 当上下文不足时应提醒学生补充问题；
5. 多轮问答记录应可查询。

---

## 3.3 进度续接与节奏调整模块

### F3.1 断点保存

当学生打断课堂时，系统应保存当前课堂断点。

断点信息包括：

1. 课堂 sessionId；
2. 当前课件页码；
3. 当前播放时间；
4. 当前课堂状态；
5. 打断时间；
6. 打断来源。

---

### F3.2 断点续播

当答疑结束后，系统应恢复原课堂进度。

功能要求：

1. 恢复原课件页码；
2. 恢复原播放时间附近；
3. 音频模式下支持 seek；
4. 视频模式下支持 seek；
5. 无音频或视频时至少恢复页面状态；
6. 断点恢复误差应尽量控制在 1 秒以内。

---

### F3.3 学习状态诊断

系统应根据学生提问和答疑情况评估学习状态。

功能要求：

1. 分析学生问题涉及的知识点；
2. 判断学生对知识点的理解程度；
3. 识别学生可能未理解的内容；
4. 生成学习状态标签；
5. 将诊断结果用于后续节奏调整。

---

### F3.4 节奏调整

系统应根据学习状态动态调整讲授节奏。

功能要求：

1. 当学生理解不足时，系统应补充解释或建议重讲；
2. 当学生掌握较好时，系统可继续讲解或加快节奏；
3. 节奏调整结果应能反馈给前端；
4. 节奏调整不应破坏课堂播放状态；
5. 教师可查看节奏调整结果。

---

### F3.5 进度可视化

系统应提供学习进度和知识点掌握情况展示。

功能要求：

1. 展示当前课件页；
2. 展示已完成学习进度；
3. 展示打断问答记录；
4. 展示知识点掌握情况；
5. 支持教师查看学生学习情况；
6. 支持学生查看自身学习进度。

---

# 5. 非功能性需求

## 5.1 性能指标

系统应满足以下性能要求：

1. 课件解析响应时间 ≤ 2 分钟 / 份；
2. 普通文本问答响应时间 ≤ 5 秒；
3. SSE 首 token 返回时间建议 ≤ 3 秒；
4. ASR 识别响应时间建议 ≤ 5 秒；
5. 断点恢复误差建议 ≤ 1 秒；
6. WebSocket 心跳间隔建议 ≤ 30 秒；
7. 系统支持并发访问人数 ≥ 10 人。

---

## 5.2 算法准确率

系统应满足以下算法指标：

1. 知识点识别准确率 ≥ 80%；
2. 智能解答准确率 ≥ 85%；
3. ASR 识别结果应满足课堂问答可用性；
4. RAG 答案应优先基于课件上下文生成。

---

## 5.3 数据集要求

系统应支持处理涵盖文、理、工、医等多学科课件。

用于训练、验证或测试的课件解析样本集规模不少于 100 份，并尽量涵盖文、理、工三大类。

---

## 5.4 安全与隐私要求

1. 系统不得在前端保存 DeepSeek、阿里云或其他第三方服务 API Key；
2. 学生语音录音仅用于 ASR 识别和课堂问答；
3. 原始音频不应长期保存，除非获得明确授权；
4. 问答记录和学习状态数据仅用于教学分析和课堂续接；
5. 日志中不得打印 API Key、Authorization、Base64 音频或完整隐私数据；
6. 系统应支持接口鉴权和访问控制；
7. 系统应防止未授权访问课程数据、问答记录和学习状态数据。

---

## 5.5 可用性要求

1. Python AI 服务不可用时，系统应返回友好错误或使用 fallback；
2. TTS 服务不可用时，前端应支持文本朗读兜底；
3. ASR 服务不可用时，学生应能够手动输入问题；
4. RAG 检索失败时，应允许系统返回基于模板的回答；
5. WebSocket 失败时，不应影响手动问答；
6. SSE 失败时，应降级为普通问答接口；
7. 系统错误提示应使用用户可理解的中文文案。

# 7. 验收与交付物要求

## 7.1 核心功能验收场景

系统应至少支持以下端到端演示流程：

1. 教师上传一个 PDF/PPT/PPTX 课件；
2. 系统完成课件解析；
3. 系统生成结构化讲稿；
4. 教师查看并可编辑讲稿；
5. 系统完成 TTS 语音合成；
6. 学生进入 AI 互动课堂；
7. 系统按页播放讲稿音频；
8. 学生通过语音或文字打断提问；
9. 系统完成 ASR 或文本接收；
10. 系统基于当前页上下文生成回答；
11. 前端以流式方式展示回答；
12. 系统展示 evidence 来源；
13. 答疑结束后从原断点继续播放；
14. 系统记录本次打断和问答；
15. 教师或学生可以查看学习进度和问答记录。

# 8. 核心关注点与评估标准

## 8.1 场景适配性

系统应高度贴合泛雅平台现有教学场景和师生痛点，能够将静态课件转化为可互动、可问答、可续播的智能课程。

## 8.2 技术创新性

系统应体现以下创新点：

1. 大模型辅助讲稿生成；
2. 基于课件上下文的 RAG 答疑；
3. 多模态输入与语音打断；
4. 智能断点续播；
5. 学习状态诊断与节奏调整；
6. 可选数字人讲授与多模态视觉理解。

## 8.3 功能完整性

系统应实现“课件解析 - 讲稿生成 - 语音讲解 - 学生打断 - 实时答疑 - 断点续播 - 学习记录”的闭环。

## 8.4 落地可行性

系统应具备：

1. 低成本部署能力；
2. 与泛雅平台轻量化集成能力；
3. 浏览器端可用性；
4. API 标准化能力；
5. 容错和降级能力。
